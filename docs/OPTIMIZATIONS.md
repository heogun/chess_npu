# OPTIMIZATIONS.md — 성능 최적화 기법 백로그 (검토 · 후속 적용 대상)

> 목적: 사용자가 제안하는 최적화 기법을 검토하고, **지금 vs 나중** 적용 대상을
> 문서로 유지한다. 각 항목은 "검토 결과 + 왜 나중/보류인지 + 시행 조건"이 기록되어
> 언제든 복원 가능한 결정 로그 역할을 한다.
>
> 규칙:
> - 상태: `적용됨` / `반영 예정` / `유보(나중 적용)` / `기각`
> - 검토는 반드시 실제 코드/숫자 기준 (파일:라인 인용)
> - 적용 시 G2 게이트(FPGA 출력 == SW 참조 바이트 일치) 재검증 필수

## OPT-001 — DSP 블록 9×9 분할 및 FC 병렬 레인화

- **제안**: 5CSEMA5(87 DSP)에서 18×19 기본 모드 대신 9×9 분할 사용 → 디바이스당
  174개 8비트 곱셈/클럭.
- **검토 결과 (수치 정정 포함)**:
  - Cyclone V DSP는 18×18 ×2 또는 **독립 9×9 ×4** 구성 → 최대 **348개** 9×9 MAC
    (`87 DSP → 174`는 과소평가).
  - NNUE FC는 int8×int8+누적으로 **정확히 9×9 슬라이스 + 내부 36비트 누산기** 매핑.
  - 현재 `fc_pipe.sv:110`은 **단일 MAC(1 MAC/클럭)**: FC0=16×1024, FC1/2 소량 →
    eval당 ~17K 사이클(100MHz ≈ 170µs). **패킹만으로는 무변화**, 병렬화가 전제.
  - 목표 형상: FC0를 P=16~32 레인으로 → DSP 4~8개, FC 17K→~1K 사이클(~11µs).
- **왜 나중인가**: 현재 마일스톤(M5 온보드 검증)은 "기능 + SW 일치"가 우선. RTL 변경 시
  fit/asm 재컴파일 + G2 재검증 필요. 인터페이스(desc/feat/result 링 + DDR 가중치
  스트리밍)는 불변이라 유닛 교체만으로 가능.
- **시행 조건/후속**:
  1. FC0 16~32 레인 MAC 프레임워크 + 가중치 뱅크 배열(OPT-002)
  2. `hps_sdram` 주파수/`hps_sdram_p0` 대역폭 프로파일 확인 (DDR 가중치가 공급 한도면
     FC 병렬도 제약)
  3. Quartus fit 리포트에서 DSP 사용량 vs 매핑 확인 (패킹 여부 — fitter가 자동 9×9
     패킹하는지 관찰)
  4. G2 재검증 (SW 참조와 바이트 일치)
- **참조**: `hw/quartus/ip/fpga_top_soc/rtl/fc_pipe.sv:110`, `fpga_top_soc.sv:32-40`

## OPT-002 — M10K 듀얼포트 풀가동

- **제안**: BRAM을 true dual-port로 구성 → 클럭당 2읽기(대역폭 2배).
- **검토 결과**:
  - M10K는 2개 독립 액세스 포트 지원(정확). "200MHz 효과" = 100MHz × 클럭당 2액세스
    로 개념 일치.
  - 현재 `fc_bram.sv`/`accumulator.sv`는 등록 리드(블록 RAM 추론됨)지만 **순차
    1읽기/클럭**이라 듀얼포트 이점 미사용. FTE 어큐뮬레이터 갱신은 "읽고-쓴다" 패턴이라
    simple dual-port면 충분.
  - 진짜 쓸모: **FC 병렬화(OPT-001) 시 k 레인이 k개 가중치 읽기/클럭 필요** →
    k/2개 듀얼포트 뱅크 또는 k개 싱글포트 뱅크로 분산, 입력 활성화 q는 브로드캐스트.
- **왜 나중인가**: OPT-001과 묶여 있고, 지금 요구 대역폭은 1읽기/클럭으로 충분.
- **시행 조건/후속**: OPT-001 진행 시 함께; 각 뱅크 모듈의 rd 프로그램 가능 활성화,
  Quartus `ram` 추론 보고서(`ram_type M10K`, dual port) 확인.
- **참조**: `hw/quartus/ip/fpga_top_soc/rtl/fc_bram.sv`, `accumulator.sv`

## OPT-003 — ACP (Accelerator Coherency Port) 브리지

- **제안**: H2F 대신 ACP 브리지 → FPGA가 L2 캐시를 직접 봐서 flush 오버헤드 제거.
- **검토 결과: 기각 (현 유지: F2H)**
  - FPGA 마스터는 **읽기 전용**(`fpga_top_soc.sv:63-69 m_f2h`)이고 결과는 FPGA BRAM
    result ring → **FPGA→HPS 쓰기가 없어** 동기화 트래픽 자체가 없음.
  - 가중치(FT/PSQT)는 **write-once / read-many** → 로드 시 1회 flush로 충분.
  - ACP는 L2 스누프·경합으로 **탐색 CPU 대역폭과 경쟁**해 NPS에 불리할 수 있고, 맵핑
    복잡도도 증가. 대량 스트리밍에는 `F2H`(현재) / 전용 **f2sdram** 포트 +
    dma 일관성/1회 `drain_write_buffer`가 적합.
- **조건부 부활** (미래): FPGA→HPS 저지연 핸드오프(예: CPU가 방금 쓴 버퍼를 즉시 읽는)
  패턴이 생기면 재검토.
- **참조**: `README.md` 게이트 G2, `docs/INTERFACE.md`, `ddr_stream.sv`

## OPT-004 — isolcpus + 스레드 고정

- **제안**: `isolcpus=1` 부팅 옵션 + 탐색 스레드 CPU1 고정 → 컨텍스트 스위칭/캐시
  지연 제거.
- **검토 결과: 반영 예정 (저비용, 무해)**
  - 듀얼 Cortex-A9: **CPU0 = 리눅스/UIO/배칭 스케줄러**, **CPU1 = 스톡피쉬 탐색 전용**.
  - bootargs: `isolcpus=1 nohz_full=1 rcu_nocbs=1 console=ttyS0,115200`
  - HW 오프로드라 CPU-bound 이득은 상대적으로 줄지만, 탐색 북키핑/타이밍 안정성에 유효.
  - 듀얼코어 기준 `Threads=1`이 적정.
- **시행**: u-boot 스크립트(`u-boot.scr`) bootargs + 스톡피쉬 실행 시 `taskset 2`
  또는 엔진 내 `pthread_setaffinity_np`.
- **상태**: 이미지 조립 단계에서 반영 예정.

## OPT-005 — 하드웨어/소프트웨어 파티셔닝 (탐색=CPU, NNUE=코프로세서)

- **제안**: 재귀 분기/가지치기(탐색)는 분기문 중심이라 FPGA의 쥐약 → ARM(1GHz)에
  맡기고, FPGA는 "보드 → 점수" 순수 코프로세서로 한정.
- **검토 결과: 이미 적용 (설계 핵심)**
  - `evaluate_hw.patch`는 `evaluate.cpp`에 `#if USE_NNUE_HW` 한 블록만 추가하고,
    **탐색/무브젠/가지치기는 전혀 수정하지 않음**. FPGA는 `{psqt, positional}`만
    반환하고, 최종 스케일 `(125*psqt + 131*positional)/128`(evaluate.cpp:64)은 SW 유지.
  - 분업 경계가 정확히 "score 계산기" 코프로세서 모델과 일치. → 유지, 재검토 불필요.
- **인접 미래 후보**: 현재 HW는 호출마다 `MODE_REFRESH`(풀 리셋)로 어큐뮬레이터를
  다시 계산하지만, 링 계약에는 `n_add/n_rem/cnt_main0...` **증분 갱신 인터페이스가 이미
  존재**(`nnue_batch.h EvalRequest`). SF 반복 호출의 FT 재계산을 제거하려면
  **증분 모드**를 활용하는 방향이 자연스럽게 다음 단계.
- **참조**: `hw/arm/evaluate_hw.patch`, `hw/arm/nnue/nnue_batch.h:22-34`

## OPT-006 — 핑퐁/더블 버퍼 (대기 0%)

- **제안**: FPGA 내 A/B 입력 버퍼로, 연산 중 다음 데이터를 미리 채워 HW·CPU 모두 idle 0%.
- **검토 결과: 부분 적용 + 유보**
  - **이미 구현된 스케일**: desc(64)/feat(64)/result(256) **링** 은 "2슬롯 핑퐁"의 일반화.
    `BatchScheduler`(thread-safe enqueue + doorbell CSR.DESC_HEAD)로 제출-완료가
    비동기 분리됨. Lazy SMP 다중 워커가 같은 링에 배칭(kind of 자동 더블버퍼).
  - **남은 idle 원인 1 (SW)**: `HwEvaluator::evaluate()`가 `enqueue → waitResult(2s)` **동기 대기**
    (`evaluate_hw.patch` nnue_hw.cpp). 단일 탐색 스레드에선 제출→대기 주기로 전환 idle 존재.
  - **남은 idle 원인 2 (HW, 본질)**: FC 단일 MAC(`fc_pipe.sv:110`) → **eval당 ~17K 사이클
    ≈ 170µs 대기 지연**. 전송 idle은 핑퐁으로 지워도 **계산 대기 자체는 안 지워짐**:
    HW 소비속도(↓)가 SW 공급속도(↑)보다 느리면 idle은 FPGA로 이동.
  - **결론/조건**: 핑퐁은 "전송 병목 제거"이지 "계산 지연 제거"가 아님. **OPT-001(FC 병렬화)이
    선행돼야 진짜 idle 0% 시나리오 성립**. 링 구조는 그대로 두고, 링이 항상 차 있게 하는
    배칭/프록시 구성 실현은 OPT-001 이후 재검증.

## OPT-007 — AXI 데이터 패킹 / 64·128비트 브리지

- **제안**: 8비트 데이터를 32비트 브리지에 통째로 태우면 24비트 낭비 → SW에서 패킹하고
  H2F 브리지 폭을 64/128비트로 확장.
- **검토 결과: 부분 적용 + 유보**
  - **실제 고대역폭 경로는 "브리지 전송"이 아님**: 가중치(FT/PSQT)는 CPU→브리지 전송이
    아니라 **FPGA가 HPS DDR3 직독**(`m_f2h`, 64비트 버스트, `ddr_stream.sv`). eval 핫패스
    대역폭은 이미 DDR 쪽에서 64비트로 해결되어 브리지 폭이 상관없음.
  - feature/desc/result 경로는 **lw 32비트 창**이지만 데이터가 `u32` 인덱스 목록
    (프레임당 ≤ 수백 워드) → eval당 전송량 **sub-µs 수준**. 32비트로 충분, 병목 아님
    (병목은 OPT-001의 FC 사이클).
  - 8비트 패킹이 "있으면 좋은" 곳은 초기 가중치 업로드(일회성, ~200MB)뿐이고, 이 역시
    `s_load`가 이미 32비트 워드로 스트리밍(주소 자동증가). → 128비트 lw 확장 이득 미미.
  - **결론**: 유보. FC 병목(OPT-001) 해소 후 실제 대역폭 프로파일로 재검토.

## OPT-008 — Lazy SMP 워커→FPGA 프록시 (하이브리드 파티셔닝)

- **제안**: N개 워커 중 1개를 "FPGA에 작업 던지고 대기"하는 프록시로 개조해, FPGA를
  추가 CPU 코어처럼 편입 + 방대한 병렬 구조 그대로 유지.
- **검토 결과: 유보 (재판정 조건 기록)**
  - **현재 설계의 개념**: 프록시 1개가 아니라 **전 워커가 하나의 `BatchScheduler`/UIO
    백엔드를 공유**해 모든 NNUE eval 을 HW로 오프로드(`evaluate_hw.patch`). Lazy SMP의
    다중 스레드 자연 제출이 곧 HW 배칭 효율.
  - **프록시 변형이 유효한 구간**: HW 지연 > SW eval 시간일 때, CPU가 HW에 블로킹되는
    것을 피하기 위해 "일부 워커=SW eval + 1 워커=FPGA 프록시" 혼용. 
  - **그러나 현재값**: HW eval ~170µs(OPT-001 전) 대 SW eval ~10µs → **모든 워커가 HW를
    쓰면 오히려 탐색이 느려짐**. 즉 'all-offload(현재 패치)' 의 실질 전제는 **OPT-001로
    HW 지연을 SW 대비 작게** 만드는 것.
  - **하이브리드 요건**: HW 패스와 SW 패스가 동시 존재하면 **점수 패리티(G2) 보장**이
    설계 조건. 
  - **재판정 트리거**: OPT-001 적용 후 HW eval latency 벤치(µs/eval, NPS)를 보고
    (a) HW < SW → all-offload 유지, (b) HW ≈ SW → 프록시 혼용 고려.

## OPT-009 — 차분 업데이트 (Δ accumulator) ⭐

- **제안**: 매 턴 전체 가중치를 재계산/전송하는 대신, 어큐뮬레이터를 FPGA에 유지하고
  "이동한 말(added/removed) 좌표만" 보내 ± 덧셈만 수행. 통신·연산량 대폭 삭감.
- **검토 결과: 우선 후보 (컨트랙트는 존재, HW/SW 둘 다 미가동)**
  - ABI: `NNUEHW_DESC_MODE_ACCUMULATE(0)` ↔ `REFRESH(1)` **이미 정의됨**(`nnuehw.h`).
  - 단, 주석 명시: **"ACCUMULATE는 FPGA v1 현재 미구현 → ERR_FAULT"**. → HW 측 Δ 적용
    유닛이 없음.
  - SW: `evaluate_hw.patch`의 `HwEvaluator`는 항상 `MODE_REFRESH`만 사용 (feature 목록으로
    스크래치 재계산). 즉 "SF 소프트웨어가 이미 증분 동작함"을 HW로 미러링하는 단계가 비어 있음.
  - **가치 근거**: SF18 eval에서 **FT(어큐뮬레이터 갱신)가 지배적. REFRESH→ACCUMULATE 전환은
    연산량(활성 피처 ~30-60 → ~4-8개)과 통신량(프레임 수백 u32 → 삭제 목록 수 u32)을 동시에
    줄이는 최대 단일 레버** — OPT-001(FC)과 별개 축.
- **시행 조건/후속**:
  1. FTE에 **지속 누산 상태**(bucket 8 × stm × persp × 256레이인) + RMW Δ(± feature vector)
     유닛 추가 (`accumulator.sv`/`fte.sv` 확장)
  2. SF 훅에서 증분 정보 추출: move 시점의 `added/removed` 목록(SF `half_ka_v2_hm` 누산 경로)을
     드라이버로 노출 — 더 깊은 패치 필요(`evaluate.cpp` 1블록 수준으로는 부족)
  3. 배칭과의 상호작용: Δ 요청이 스레드별 누산 상태를 공유하지 않도록 시퀀스 규약 정의
     (각 스레드 자체 accumulator 스택 유지 = SF 방식)
  4. G2 재검증 (REFRESH 경로 결과와 byte 일치)
- **참조**: `hw/arm/nnuehw/nnuehw.h` MODE 정의, `hw/arm/evaluate_hw.patch` (HwEvaluator),
  `hw/arm/nnue/nnue_batch.h:22-34` (EvalRequest n_add/n_rem)

## OPT-010 — 제로 스킵 (희소성 극대화)

- **제안**: 연산 파이프라인 앞단에 0 비교기 → 입력이 0이면 DSP 스킵(주소 점프). ReLU 후
  상당 출력이 0이므로 2~3배 체감 속도.
- **검토 결과: 유보 (한정 유효, 정확한 희소 위치 관리 필요)**
  - **이미 자연 스킵**: FT 입력은 "활성 피처 인덱스 목록" 전송 = **희소를 구조적으로 이미
    반영**(빈칸 64칸이 아니라 active index만 나감). 제로 스킵의 대부분은 사실상 이 경로에서
    완료됨.
  - **밀집 구간**: FC0 입력 `q[i]`는 **quantize 후의 accumulator 값으로 밀집**(int8, 0이 거의 없음).
    zero-skip이 유효한 곳은 fc1/fc2의 post-ReLU 입력뿐인데 **이 계층은 32×32/32로 미미**.
  - 동적 스킵 = 매 클럭 가변 점프 제어(FSM 복잡도↑, BRAM 읽기 순서 파괴) 대비 이득이 작음.
  - **결론**: 별도 회로 추가보다 **OPT-009(Δ)가 희소 이득을 이미 흡수**. 유보/재검토.
- **참조**: `hw/quartus/ip/fpga_top_soc/rtl/fc_pipe.sv:102-107` (q 입력 밀집)

## OPT-011 — 가산기 트리 (병렬 MAC 어레이)

- **제안**: 16개 곱셈 결과를 순차 합산(16 사이클)하지 말고, 파이프라인 레지스터를 낀
  이진 가산 트리로 매 클럭 16개를 ~4 사이클에 스트리밍.
- **검토 결과: 설계 원칙 채택 (OPT-001/FC 병렬화의 구현 세부)**
  - 수식적으로 **OPT-001과 동일 항목**의 마이크로아키텍처: P레인 9×9 MAC(아키텍처) → 이진
    가산 트리 + 파이프라인(구현 구조).
  - 포함 사항: DSP 내부 36비트 누산기 활용, 가산 트리 높이 = ⌈log2 P⌉, 파이프라인 단계 수는
    Fmax(100MHz)에 맞춰 조정.
  - 이 트리 구조는 FTE 어큐뮬레이터의 **256레이인 병렬 벡터 합산**에도 동형 적용 가능
    (OPT-002 뱅크 배열과 결합).
- **시행 시점**: OPT-001 진행 시 도입. 이 항목은 "레버"가 아니라 "구현 방식"으로 기록 유지.
- **참조**: `fc_pipe.sv:110` (현재 직렬 MAC → 교체 대상)

## OPT-012 — 활성화 함수(ClippedReLU) LUT화

- **제안**: `if (x>127)...` 분기 대신 M10K를 LUT로 써서 주소입력→답, 1사이클 리드.
- **검토 결과: 기각 (부분수용)**
  - **입력 폭 문제**: `ac7/sqr7` 입력은 int32(→ 불가능한 4G 엔트리). 16비트로 클램프 선행
    후 LUT해도 함수당 64K×8b = 512Kb ≈ **M10K 수십~백 블록 소모** → 자원 대비 이득 나쁨.
  - **현재 활성화 로직 비용은 이미 작음**: `ac7`(shift+clamp = 로직 깊이 2~3), `sqr7`는 1개의
    곱셈(DSP 9×9 1개면 충분) — Fmax 병목 아님.
  - **실질 타이밍 위험은 따로 있음**: `fwd_div32 = fwd_q / 32'sd8128`(fc_pipe.sv:116) — **가변
    나눗셈(32비트)이 로직을 크게 만듦**. → LUT 대신 **고정 역수 곱셈(`× round(2^k/8128) >> k`)**
    변환이 맞는 답. (산술 G2 재검증 필수)
  - **수용안**: 분기 clamp는 유지, `sqr7`는 DSP 매핑, `÷8128`은 역수곱으로 교체 후 Fmax 측정.
- **참조**: `hw/quartus/ip/fpga_top_soc/rtl/fc_pipe.sv:112-119, 307-319`

> CPU-bound이므로 데스크톱 i9/Ryzen9급 NPS는 물리적으로 달성 불가. 올바른 벤치 기준은

> 최대 배율을 내는 것이 목표다.

## OPT-013 — Zero-Copy 통신 / F2SDRAM 마스터 (Scatter-Gather DMA)

- **제안**: CPU가 데이터를 주지 않고, FPGA가 F2SDRAM 브리지로 메인 RAM의 큐를 직접
  퍼감. CPU는 "주소/개수" 한 줄(명령어)만 내리고 탐색으로 복귀.
- **검토 결과: 부분 적용 + 유보**
  - **가중치 경로는 이미 Zero-Copy**: eval 핫패스에서 FPGA(`m_f2h` 64비트 버스트,
    `ddr_stream.sv`)가 **CPU를 거치지 않고 HPS DDR3(FT/PSQT)를 직접 읽음**. 이 팁이 제거하려는
    "CPU가 가중치를 나르는" 비용은 이미 존재하지 않음.
  - 남은 CPU 전송은 lw 창의 descriptor/feat 제출(인덱스 목록)뿐인데 **sub-µs 수준으로
    병목이 아님**. 명령 한 줄 + 복귀는 이미 doorbell(`CSR.DESC_HEAD`) 방식.
  - **진짜 갱신 후보는 "링/디스크립터를 FPGA 창이 아니라 DDR 버퍼로" 이동** + F2H→**F2SDRAM**
    포트 전환(전용 고대역폭 경로). 비용: 커널 버퍼 일관성/플러시 규약 + 주소 계약 확장.
  - **가치 판정**: F2SDRAM은 스트리밍 대역폭에 유리하나, 현재 병목(FC 병렬) 해소 이전엔
    실질 효과가 없다. OPT-001 후 대역폭 프로파일로 재판정.
- **시행 조건/후속**: (a) `sys_sdram_f2h` 포트 구성 + 스트리밍 엔진 주소 경로 분기,
  (b) desc/feat 링을 `dma_alloc_coherent` 버퍼로, (c) OPT-001 후 벤치.
- **참조**: `hw/quartus/ip/fpga_top_soc/rtl/fpga_top_soc.sv:63-69`, `ddr_stream.sv`

## OPT-014 — 비동기 클럭 도메인 교차 (100MHz 버스 ↔ 200MHz 코어)

- **제안**: PLL로 200MHz 생성, AXI(100MHz) ↔ NNUE 코어 사이 Async FIFO. DSP/M10K는
  200MHz 이상 충분 → 연산량 물리 2배.
- **검토 결과: 유보 (저위험 전술)**
  - 타당: HPS 버스(HPS 클럭 도메인)와 내부 연산코어 분리는 표준적인 CDC 구성이므로
    구조 위험이 낮음. Async FIFO/`altera_std_synchronizer` 적용.
  - **단, 현재는 효과가 한정적**: FC가 1 MAC/클럭 직렬이라 200MHz로 올려도 단순 선형 개선일
    뿐, **OPT-001(병렬) 선행 시 배율이 극대화**됨. FTE/어큐뮬레이터는 BRAM 리드 대역폭
    지배 → 200MHz가 실제로 대역폭을 2배로.
  - DDR 스트리밍(m_f2h)은 HPS 클럭 도메인에 묶여 있으므로, 200MHz 코어로의 진입 지점에만
    CDCFIFO를 배치하는 구조로 정리해야 함 (F2H 데이터 → 패키징 FIFO → 200MHz 영역).
- **시행 조건/후속**: OPT-001 이후. Fmax(200MHz) 목표로 MAC 트리 파이프라인 재-파이프라인 +
    TimQuest 재검증. G2 재검증.
- **참조**: `fpga_top_soc.sv` (클럭 계약), `fc_pipe.sv:110`

## OPT-015 — Magic Bitboard 수 생성(Move Gen)의 1클럭 하드웨어화

- **제안**: 64비트 shift/AND/OR는 와이어 병렬 1사이클 — 슬라이딩 공격/수 생성을 조합회로로.
- **검토 결과: 기각 (통신·동기 지연이 이득 잠식)**
  - 하드웨어 능력은 맞음(비트연산 = 조합 논리). 문제는 **호출 패턴과 커플링**:
    - 수 생성은 **탐색 제어흐름과 동기적**(make→movegen→순서정렬→가지 탐색→unmake).
      eval과 달리 **비동기 배칭이 불가** — 노드마다 CPU가 FPGA에 점유/공격 목록을 보내고
      결과를 **받을 때까지 대기**하는 왕복이 생김.
    - 왕복(리퀘스트 2B + 응답 수십 바이트 + 동기화)은 mmap/IRQ 왕복 **sub-µs~µs** 수준.
      ARM A9에서 SW 수 생성은 보통 ~1µs 내외 — **HW 오프로드 순이득이 거의 없거나 손해**.
    - 순서 정렬(MVV-LVA/killer/history/SEE), quiescence 캡처 반복 호출 등 **CPU 의존
      휴리스틱과 맞물려** 오프로드 시 인텐스 반복이 오히려 늘어남.
  - eval(배치 가능, Φ당 1회)과 달리 movegen은 "탐색 1노드당 수회"·"즉시 소비" → 통신 지배.
  - **재검토 조건**: 왕복 지연을 제거할 수 있는 "전 노드 선제 수 생성 배치"(예: 몇 깊이 앞
    movegen 미리 전송) 구조가 설계상 실증될 때만. 현재로선 기각이 자원의 최선 배치.
- **참조**: SF `movegen.cpp`/`magic` 구조, `evaluate_hw.patch`의 배칭(tb 교훈)

## OPT-016 — Power-of-2 양자화 (Shift = 무곱셈)

- **제안**: 가중치를 2의 거듭제곱(±2^k)으로 제약해 곱셈을 shift로 대체, DSP 제로화.
- **검토 결과: 기각**
  - **G2 위반**: 게이트는 "FPGA 출력 == SW 참조(원본 int8 가중치 기반) byte 일치". 가중치를
    2의 거듭제곱으로 바꾸면 psqt/positional 채가 바뀌어 **byte 일치가 무너지고 재검증 전체가
    무의미**해짐.
  - **재훈련 = 엔진 강도 손실**: SF 네트 임의 변형이 아니라 재훈련은 SF 트레이닝 파이프라인과
    막대한 컴퓨트가 필요하고, 2의 거듭제곱 양자화는 int8보다 훨씬 거칠어 **평가 정확도/엘로
    손실** — '무료 곱셈'보다 강한 엔진이 우선인 이 프로젝트와 상충.
  - **전제 오류**: "DSP 87개 다 쓰면 확장 불가"는 현재 사실이 아님 — FC 병렬화(OPT-001)는
    **DSP ~8~16개면 충분**하고 M10K/ALM이 오히려 여유. DSP 부족이 병목이 아님.
  - **대안**: int8×int8(DSP 9×9) + 가산 트리(OPT-011) 표준 유지 — 성능+정확성 동시 확보.
- **시행 조건**: 없음(기각 유지). 다만 "가중치 압축(예: 2바이트→1바이트 FT)" 계열은 별도 후보로만
  기록 가능.
- **참조**: README G2 게이트, `ref_eval` (원본 가중치 산술 기준)

## OPT-017 — 실시간 가중치 디컴프레션 (On-the-Fly Weight Decompression)

- **제안**: DDR에 가중치를 RLE/Huffman으로 저장, F2SDRAM 수신 후단의 1클럭 디컴프레서가
  Zero-Deflation 스트리밍 → 대역폭 2~4배.
- **검토 결과: 유보 (위치는 정확, 전제는 과장)**
  - **위치 정확**: 스트리밍 수신 후단 압축해제 파이프라인은 요구사항이 적절
    (인플라이트 압축 데이터 → BRAM 뱅크 전개). RLE↔Huffman 혼합 파이프라인 구성.
  - **전제 1 — FC 경로는 이미 DDR-bound 아님**: FC 레이어 가중치는 수십 KB로 **M10K BRAM에
    상주 캐시**(로드 1회, 배치 64슬롯 전체가 공유). FC 핫루프는 BRAM에서 읽으므로
    "레인 32~64 → 메모리 병목" 주장은 FC 경로에 성립 안 함.
  - **전제 2 — 압축률 과장**: FT/PSQT는 **near-random 소수 int16 델타** 스트림이라
    RLE 수익은 미미, Huffman도 사실적 1.3~1.6x ("2~4배"는 비현실적). 또 1클럭 Huffman
    디코드는 가변 비트길이 심볼이라 멀티클럭 파이프라인이 필수(1클럭 불가).
  - 실질 대상은 **FT 행 인출**(상주 불가)뿐 — OPT-009(Δ)가 이미 FT 재인출 자체를 줄임.
- **시행 조건/후속**: OPT-001/009 후에 FTE 경로가 **메모리 바운드로 전환**됐는지
  대역폭 프로파일로 확인했을 때만 검토. 그때도 압축은 "주소 계약 확장 + 디컴프레서
  G2 재검증" 비용을 동반함.
- **참조**: `ddr_stream.sv` (수신), FT/PSQT 메모리 매핑 계약

## OPT-018 — 탐색 트리 파이프라이닝 / OoO 비동기 Eval

- **제안**: CPU는 eval을 던져놓고 타 분기를 탐색(Fire-and-forget), FPGA 완료 인터럽트
  콜백으로 백프로파게이션 → CPU/FPGA 지연 0.
- **검토 결과: 부분 적용 + 유보 (실용 동시성은 이미 확보)**
  - **이미 확보된 것**: 64슬롯 링 배팅 + 2코어·2스레드(isolcpus, OPT-004) → 워커는
    배치 도중 대기하더라도 FPGA의 배치 연산시간(수십 µs) 동안 CPU는 다음 노드의
    make/unmake·퀴즈 등을 진행. 구조적 파이프라이닝은 완성.
  - **Fire-and-forget의 근본 문제**: SF 탐색은 **점수에 즉시 의존**함(베타-컷오프, 무브
    오더링(killer/history/SEE), 대기). 점수를 비동기로 받으면 무브 오더링이 비결정적이거나
    프루닝 결정이 지연됨 → **강도 저하 + 재현성 상실** 위험. "백프로파게이션 콜백"은
    검색 트리 재구조화(연속체 평가 스타일)로, 검증 표면이 큼.
  - 실질적 인센티브도 작음: eval을 던진 직후 "버릴 수 있는" 여분 일이 수백 µs 단위로
    일관되게 남는 게 아님(탐색은 평가에 연쇄 의존).
- **판정**: 유보. 재검토 조건 — OPT-001로 eval 지연이 ~1K사이클 이하로 내려가면 블로킹
  대기가 소멸하므로 "비동기화" 자체가 무의미해짐. 그전엔 배팅+2스레드가 정답.
- **참조**: `evaluate_hw.patch` (HwEvaluator 대기/배치), OPT-004, `nnue_batch.h`

## OPT-019 — Move-Only 델타 인젝션 + FPGA Shadow Board

- **제안**: 16비트 Move만 전송, FPGA가 Shadow Board 비트보드로 이후 상태를 자체 파악해
  어큐뮬레이터 델타 트리거 → AXI 트래픽 소멸.
- **검토 결과: 기각 (복잡도 대비 이득 불일치 + G2 위험)**
  - **탐색은 '보드 1장'이 아님**: 재귀 make/unmake 스택(각 경로의 부분 상태)을 미러링해야

  - **체스 규칙 전면 재구현 필요**: en passant 포획 사각 처리, 캐슬링(킹/룩 동시 이동),

    (그래야만 G2 유지).
  - **절약은 소량**: 16비트 Move vs feature 목록(수십 바이트) — AXI 트래픽은 원래 작음,
    이 구간은 병목이 아님.
  - **대안(정답 형태)**: **OPT-009**가 동일 목표를 복잡도 없이 달성 — CPU가 **SF 자체 누산
    경로**로 added/removed 인덱스를 산출(→ G2 보존), HW는 ±행 합산만. Shadow board에
    쏟을 검증 자원이 거기서 훨씬 가치 있음.
- **참조**: `nnue_batch.h:22-34` (n_add/n_rem), OPT-009, SF accumulator update 경로

## OPT-020 — Qsys/인터커넥트 바이패스 (커스텀 초경량 AXI 래퍼)

- **제안**: H2F/F2SDRAM 포트를 물리 핀 Export로 빼서 커스텀 1~2클럭 크로스바로 교체.
- **검토 결과: 기각 (대부분 이미 달성 + 잔여분 제거 불가)**
  - **이미 반영됨**: `fpga_top_soc.sv`의 nnue 창은 **Qsys 인터커넥트 없이 단일 AXI4 슬레이브

    있어 소프트 로직으로 제거 불가(핀 Export 동등 개념 — 인터페이스는 이미 물리 직결).

  - 커스텀 크로스바 도입은 타이밍 클로저·검증 부담만 늘리고 성능에선 무이득.

## OPT-021 — DSP 시간 분할 다중화 (300MHz 폴딩, TDM) ⭐

- **제안**: DSP/M10K 물리 클럭 여유(실제로는 ~300MHz+ 가능)를 이용해, 100MHz 버스·제어와
  별개인 **300MHz 연산 코어** 도메인을 만들고 Async FIFO로 데이터를 주입. 87개 DSP를
  시간 폴딩 → 100MHz 등가 261(×2: 9×9 패킹) ≈ 500+ MAC/클럭.
- **검토 결과: 채택 (OPT-001 병렬 라인의 증강 항목, 2번째 다이빙 포인트)**
  - 수리적으로 타당: MAC 개수 = DSP 수 × 3300MHz/100MHz, 폴딩×패킹 = 순수 승수.
    **단, 승수가 실효가 되려면 병렬 워크가 있어야 함** → 1-MAC 직렬 파이프(현재)에서는
    사상자가 클 뿐만 아니라 300MHz라도 단일 MAC만 유지됨. **OPT-001(병렬 레인) 후에만
    TDM이 배율**이 됨.
  - 실제 한정 요소는 클럭이 아니라 **BRAM 읽기 대역폭(가중치·입력)과 DDR 스트림** —
    TDM은 이 둘을 늘리지 않음(비례 요구). 그러므로 FC 병렬 레인 수와 **M10K 듀얼포트
    뱅킹(OPT-002)** 이 먼저 균형을 이뤄야 함.
  - **시행 형태**: 100MHz 버스/CSR ↔ 300MHz 코어 사이 CDCFIFO 배치(OPT-014의 극단화),
    파이프라인 재스테이징 + TimQuest Fmax(300MHz) 검증.
- **시행 시점**: OPT-001 안정화 직후 → 분해 최적화 순서의 2단계.
- **참조**: `fc_pipe.sv:110` (1MAC), OPT-001/002/014, `ddr_stream.sv`

## OPT-022 — Zero-DDR 지식 증류 (M10K 500KB 스튜던트 피닝)

- **제안**: SF18 원본 NNUE 대신 PC에서 재학습한 ≤500KB "학생 모델"을 M10K에 100% 피닝,
  외부 DDR 접근 0 → 대역폭·타이밍 제약 소멸.
- **검토 결과: 기각 (G2 근본 위반 → 프로젝트 목표와 교차 금지)**
  - **G2 사멸**: 게이트는 "FPGA 출력 == SF18 원본 가중치 기반 SW 참조의 **byte 일치**".
    학생 모델은 가중치가 달라 같은 평가값을 내지 않음 → **정의상 G2 불가능**.
    (사용하려면 "커스텀 가중치를 SW/FPGA 양쪽에 적용" = SF 포크로, G2 개정 필요.)
  - **물리적으로도 불가**: SF FT 테이블 단독이 512KB(1024×256×int16) — M10K 500KB에
    **원본 네트는 이미 안 들어감**. 축소판은 엘로 대폭 손실(PicChess급) 예상.
  - **커스텀 넷 방향 자체는 실재하나** 스코프 외부: 별도 프로젝트(net 교체 + 검증 파이프라인).
  - **실질 대안**: DDR은 문제가 아니라 **자산** — F2H 직독이 이미 효과적. "DDR 접근 0"은
    목표가 아님(전력·타이밍은 현재 병목이 아님).
- **참조**: README G2 게이트, FT 512KB 매핑, OPT-013 (Zero-Copy/대역폭)

## OPT-023 — 2D 시스톨릭 어레이 (TPU 스타일)

- **제안**: 중앙 트리 대신 이웃 PE 간 그리드 수송(가로 가중치/세로 입력/대각선 누산) →
  장선 0, ALM 95%에도 타이밍 유지.
- **검토 결과: 설계 지침 채택 (독립 레버 아님)**
  - **하드웨어 사실**: 시스톨릭은 **연속 스트리밍 대형 GEMM**에서 효율 — 우리 FC0는

  - "ALM 95%에서도 위반 없음"은 마케팅식 단언일 뿐, 일반적으로 보장 불가

- **시행 시점**: OPT-001 FC 어레이 구현 시 적용되는 배치 원칙.
- **참조**: OPT-001/011, Cyclone V 구현 툴 (라우터 배치 가이드)

## OPT-024 — LUT-Net / BNN-XNOR-Popcount

- **제안**: ±1(또는 0) 이진 가중치, XNOR+Popcount로 MAC 교체, DSP 0개, 수만 병렬 연산.
- **검토 결과: 기각**
  - **메트릭 오류가 핵심**: "NPS 슈퍼컴퓨터급"은 **로우(op/s) 벤치**일 뿐. 체스 강도는

    10배여도 엘로는 SF18에 크게 밀림(이진 체스넷은 데스크톱에서도 실증적으로 약함).
    NPS를 지표로 삼으면 안 되는 전형적 예.
  - **G2 위반**: 가중치·활성화 모두 바뀌어 SF 참조와 구조적으로 불일치(OPT-016과 동일).
  - **구조 불일치**: FT 어큐뮬레이터 단계는 int16 누산으로 **이진화 대상이 아님** —
    BNN은 전 계층 이진이 전제.
  - **동기 부재**: DSP는 병목이 아님(FC ~16개 필요). 곱셈기를 없애야 할 이유가 없음.
- **참조**: OPT-016 (동일 카테고리 기각), SF 9차 NNUE 정확도 민감도

## OPT-025 — HW Quiescence Search (마이크로서치 오프로딩)

- **제안**: qsearch 뎁스 1~3을 FPGA 내부 FSM + HW 무브젠으로 전개, 최종 안정화 점수만 반환.
- **검토 결과: 기각 (범위·위험 불일치) + 기존 설계와의 정합성 기록**
  - **틀린 전제는 "qsearch 비용의 정체"**: qsearch 노드의 지배 비용은 **리프 eval**
    (NNUE) — 이미 **현재 설계의 HW eval이 정확히 이 병목을 공격**함(배칭으로 64슬롯).
    qsearch는 실제로 'eval 가속기가 이미 위본당하는 자리'임.
  - **남는 부분이 HW로 안 풀림**: 캡처 legality/SEE/고격 순서(오더링)·TT·killers·PV·
    rep/50수 — 전부 **CPU-의존 데이터 구조와 상태**. HW 분기부(베타 커트)까지 옮기려면
    "SF qsearch를 노드 단위로 그대로 포팅"해야 하고, 점수가 SW와 1비트 다르면
    **G2 위반 + 탐색 강도 변동**.
  - **커플링 역행**: OPT-015(무브젠) 기각의 동일 사유 — qsearch 진입/리프마다 CPU가
    HW 미니서치 결과를 **동기 대기**. 2스레드 설정에선 스레드 블로킹이 SW보다 길어질
    수 있음.
  - **진짜 2번째/3번째 다이빙 포인트는 별도 항목에 명시**(OPT-009 Δ 옴, OPT-021 TDM).
  - 기록: "qsearch 가속 = HW eval이 이미 처리 중" 으로 봉인 — 향후 커스텀 넷/개정 G2
    프로젝트에서만 재고 가능.
- **참조**: `evaluate_hw.patch` (eval 오프로드), OPT-015(무브젠 기각 근거)
